# 方案触发与询问退回修复

2026-10-12，独立分支 `codex/plan-trigger-fix`，基线 `aa4a96ff`。本地候选前端 5220、API 3120、独立数据库 `ta_case_agent_plantrigger`；5199、3106 及原业务记录保留。

## 已确认原因

截图 Case 的第 8 轮在 09:33 完成了方案和执行契约整理。第 9 轮 09:34 用户只问“下一步是什么？”，但 `beginCaseDiscussionTurn` 对任何普通讨论都先把待确认方案退为草稿；随后读取的快照已是草稿，AI 因而提示重新整理。文字“继续下一步”和“直接给我整理方案”此前已经进入过真实方案节点，因此不能把问题归结为前端完全没有文字触发入口。

隔离浏览器另复现按钮进入方案节点后，结构化预期失败而仅保留草稿。真实模型把申请金额误作确认金额、把确认份额误作持仓总份额，还从 `evidence` 引用不在 `expected` 中的文字。严格校验正确拒绝；旧修复指令笼统要求“不删断言”，与移除模型额外添加的无依据断言相冲突。

修复过程中进一步复现：预期文字“申购申请以金额确认成功，状态为CONFIRMED……”被逗号拆开后，前半句被误判为缺少状态，从而产生假待澄清问题。另有模型把未要求核验的可选结果字段列成缺失；这种情况即使契约格式有效，仍只能留在草稿，不能算生成成功。

## 行为变化

- 内部路由增加只查询已有方案的动作。询问内容、进度、下一步和仅认可现有方案时保留待审阅状态及已有确认；修改条件、取消和重新整理继续使用原失效流程。草稿承接明确整理建议的“继续”仍生成方案；已待确认方案的“继续”引导真实确认入口。
- 查询回合可以在方案待确认时完成；回合尚未完成时，服务端阻止另一请求并发确认方案。失败后重试原查询复用原回合，不重复路由或撤销方案。
- 预期构造使用现有数值校验器从每个场景原文提供可绑定字段、值、比较方向及未支持字段，减少把输入和观察说明误作结果。校验和业务原文保留规则不变；不自动删除错误断言来跳过校验。修复回复必须纠正或移除模型额外添加的无依据内容，同时保留用户明确要求的断言及业务预期。
- 同一操作的成功/失败表述后紧跟逗号及一致、正向、明确的状态字面值时，不再增加假待澄清问题；跨业务、分号隔开的结果、否定、疑问及相互矛盾状态仍保持澄清。未要求的可选协议字段不得因为没有原文数值就列为缺失信息。
- 重新整理时传入当前草稿的业务目标、条件和场景；历史生成回复不再把旧契约、失败诊断及假缺失反复注入新方案。普通业务讨论和用户消息仍保留；契约构造以当前方案及用户消息为依据。由后端生成的状态澄清问题根据当前内容重新计算，其他真实业务问题不删除。
- 内部失败记录增加具体原文绑定原因，客户界面继续保留真实草稿及失败提示。未增加依赖、数据库迁移、UI 样式或案例专用业务字段。
