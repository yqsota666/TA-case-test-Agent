# 对话推进与方案可靠性修复设计

2026-10-11。基于 `29c37109` 平台代码与本分支真实模型实验。本文件记录实施前设计。核心修复已在独立功能树实施，实际范围与验证结果见《对话推进修复本地验收》；设计条目不能单独作为完成证明。

## 决策

保留现有 LangGraph、协议能力、工作流与确认界面。增加服务端动作决策，拆开业务草稿与可执行契约，并让校验错误返回产生错误的阶段。按三个独立增量实施，避免更换 Agent 框架或只扩充前端关键词。

成功标准是：新手给出样例并要求推进后，系统能展示已有信息形成的可编辑审阅内容；明确区分可确认的有效方案与仍有问题的草稿；真正缺失的业务条件才向用户询问。普通聊天认可仍不能替代准备数据、预期结果两次明确确认。

## 证据与修复位置

| 实验或代码证据 | 修复责任 |
| --- | --- |
| 当前短句路由只识别 1/13 个应生成请求；工具路由两轮识别 26/26 | 服务端上下文动作决策，前端不再以正则决定 `/discussion` 或 `/plan` |
| 相同“继续”在 JSON 路由中有一次漏判 | 持久化明确的待推进动作，不能从上一条 AI 固定措辞推断 |
| `UNPLANNED` 没有步骤仍进入申请契约生成 | 在方案阶段建立分支和前置校验，保存待补全草稿，停止依赖未成立的下游调用 |
| 同包发送顺序误建成步骤依赖；重答只修改下游契约 | 将包内顺序与跨包结果依赖分开，修复上游后重新派生下游 |
| 申请金额被绑定成确认金额 | 保留字段的业务角色和证据来源，校验绑定语义；不得删掉断言换取通过 |
| 真实实验发生 HTTP 429 | 服务端统一请求预算与限流，限次退避，保存重试点；限流不能降级成“用户没有提供足够信息” |

工具调用仅在本次小样本中表现更好，并不保证一般场景的准确率。详细数据和实验限制见《意图路由真实模型实验》。

## 一、服务端统一决定下一步

新增对话编排入口，读取真实 Case 状态、已保存的草稿、用户当前输入、必要历史和待推进动作。模型通过受约束的工具调用提出动作；服务端验证动作和参数后调用现有服务。先支持讨论、整理审阅方案、修改草稿、澄清四类必要行为，避免一次铺开所有 Agent 能力。

前端按钮和自然语言共用同一动作注册与校验。原 `/plan` 入口可保留兼容，但必须经过相同服务端权限与阶段检查。系统允许整理草稿时，“继续下一步”“现在可以生成吗”可以触发整理；不要求特定句式，也不要求积累两条 AI 回复才允许生成。应去掉现有以讨论轮数替代业务准备度的硬门槛，保留实际输入与状态校验。

取消、否定、解释、引用、条件句不能被简单命中词触发。“修改金额，然后整理”必须先应用有来源的修改再整理。“继续”的指代由实际待推进动作和本轮语义共同判断；新指令优先，不能让历史待办覆盖取消或改口。

待推进动作由系统成功完成的步骤和向用户提出的具体建议产生，保存时绑定 Case 修订号，条件变化即失效。不能把任意 AI 自述“已确认”当作系统状态。缺乏唯一指代且会导致不同操作时才澄清。

本阶段工具不开放提交 TA、锁定数据或确认预期的聊天授权。模型返回未知工具、无工具或非法参数时进入明确的受控失败处理，不默默退回普通讨论并让用户再猜入口。

## 二、先建立可审阅业务草稿，再派生执行结构

将需求与业务草稿作为可独立保存的产物：共同条件、各情况差异、预期、解释、未决问题及模拟假设。字段与情况数量随 Case 变化，非对比 Case 保留自己的结构。原始对话保留，提取内容记录来源；用户修改只更新相关条件，不能丢失其他已给信息。

草稿不要求用户知道协议字段名。系统可负责的申请序号、账号引用、协议格式由现有后端能力处理。业务规则缺失时可以展示已有草稿与真正需要补充的问题；待补全草稿不能启用执行确认，也不能冒充完整可执行方案。有效方案继续进入现有准备数据与预期审阅界面。

先检查业务草稿与文件安排，再构造依赖它们的数据和预期契约。`UNPLANNED` 应返回业务草稿和具体未决问题，不调用缺少发送步骤的申请生成。补齐条件后从文件安排阶段恢复，不只是生成一段澄清文字后继续处理旧方案。

取消或输入变化时只保存符合当前修订号的结果；旧模型请求即使稍后完成，也不能覆盖用户的新条件。

## 三、把协议规则交给可验证的代码

模型负责理解业务目标、描述条件与预期、提出操作意图；已有协议模块负责校验字段、生成系统字段和合法引用。优先在当前支持范围内增加确定性构造，逐步缩小模型自由生成低层关联结构的范围，不另造一套与协议库平行的规则。

对 TA 操作至少区分三件事：申请操作之间的包内顺序、提交包划分、提交后回传结果依赖。相同通道、业务日期和依赖条件的申请按类型合批，完整保留各账户记录和预期。01/03 同包、OFI 标明顺序、一次 ZIP 提交；新账户03依协议引用同账户01，不能编造未知TA账号。02/04真实回传后才更新正式资源。

有未来结果依赖或不同业务日期的操作明确划分实际提交包，不能机械删除依赖来过校验，也不能把所有 SEND 依赖都视为同一种错误。新设计与既有契约版本要明确适配，历史确认方案保持原语义。

申请输入金额与回传确认金额必须分别绑定证据。若用户只给申请金额，不自动宣称确认金额相等；允许的合成预期要显式标为假设。没有协议绑定的业务分析仍可保留为业务预期，不强行改成后端接入任务。

## 四、按错误所属阶段恢复

校验结果逐步增加机器可读的错误类型、字段路径、所属阶段及关联证据，同时保留现有校验器作为最终边界。例如文件步骤依赖错误返回文件安排阶段，预期字段错绑返回预期映射阶段，缺少业务规则才进入用户澄清。

每个阶段先校验，再调用下游。上游变化后使受影响的下游产物失效并重建，保留有效业务条件；不能拿固定的错误上游反复要求下游重答。每轮设置总调用、耗时和自动修复预算，相同错误重复出现即停止盲重试，保存草稿与失败点供继续处理。具体预算以真实模型串行验收结果确定，不承诺实验尚未支持的耗时目标。

429、超时和模型格式错误与业务缺失分开处理。短暂故障有限退避重试；超预算后保留内容并提供“重试整理”。用户只看到简明原因和有效下一步，日志记录诊断细节。不能向用户说“你需要补齐技术字段”或泛称“系统不能生成”。

持久化事务、请求幂等键和 Case 修订校验应覆盖一次动作的开始与结果提交。工作流仅以真实保存和校验结果推进；流式文本、模型自述或中间内存对象都不是成功依据。

## 五、用户实际会看到什么

在当前页面适当位置恢复一个“整理为审阅方案”入口，不改变整体布局与材质。按钮用于发现和兜底，自然语言仍可直接调用相同能力。不能因恢复按钮而要求用户必须点击它才能生成。

例如用户说“那你现在可以生成吗”：系统理解为整理请求，应用最新条件，展示可编辑审阅内容。若执行结构还在修复，则明确显示草稿和真实状态；若存在业务阻塞，则同时显示已有内容和具体问题。合法方案保存后进入已有确认流程，不再回复一段关于按钮和状态机的解释。

用户说“先别生成，我再改金额”：停止待生成动作并更新条件。用户仅说“可以”：根据上下文可以承接整理草稿，但不能替代两次明确点击确认。

## 六、实施与验收

三个可独立回滚的增量，均在本地功能分支进行：

1. 服务端动作入口与上下文决策，接通现有 UI/API，恢复整理入口，加入请求幂等与修订校验；先解决漏触发，并如实显示现有生成失败。
2. 草稿独立保存、阶段前置检查与 TA 操作构造，解决无步骤仍向下生成及包内顺序混淆；接入现有确认界面。
3. 分阶段修复与继续处理、限流和取消恢复，完成真实模型、真实本地持久化和浏览器全链路验收。

每一步都验证自然语言和按钮走同一服务端边界。阶段1完成不代表事故解决；完整验收必须覆盖阶段2、3。

验收以产物和流程为准，不能只报意图识别准确率：

- 脱敏复现事故的完整上下文与最新修改，真实模型产出合法可保存方案；浏览器实际展示，进入准备数据确认；不动原用户Case。
- 使用未参与路由设计的表达，覆盖推进、修改后生成、取消、仅解释、条件句、引用以及同一句“继续”的不同上下文。
- 不同对比数量、字段、长文本、缺失业务规则和非对比 Case；缺失规则要保留草稿并准确澄清，不能靠编造通过。
- 同包01/03、多账户合批、真实跨日期和未来回传依赖；历史确认方案语义保持。
- 注入上游依赖错误、错绑预期、`UNPLANNED`、429、超时、重复请求及生成途中修改；验证修复责任、预算、草稿保留、无重复提交和旧结果不覆盖新输入。
- 验证真实数据库保存、HTTP/SSE反馈、工作空间隔离以及两次明确确认；没有确认前不得产生执行或正式资源。
