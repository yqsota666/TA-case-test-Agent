# RR 等锁后的写入校验审查

审查集成树 `07c24b45` 的写事务，不调整 MySQL REPEATABLE READ 隔离级别。鉴权普通 SELECT 建立的快照不会因为后续 FOR UPDATE 等待成功而刷新；业务校验必须使用当前读。

## 已修复并复现

新增 `write-snapshot-race.mysql.test.js` 使用独立临时库、两个真实连接：第一个持有 Chat 锁，第二个完成鉴权并建立旧快照；第一个提交修改后第二个继续。未修改版本复现以下五种结果，修复后同一夹具通过。

- 草稿确认读旧 revision，成功确认用户尚未审阅的新 revision。确认和编辑的 revision、已有确认记录改为锁读。
- 等待中的编辑看不到新提交的数据确认，成功修改已确认草稿。确认记录当前读阻止该编辑。
- 发文批次看不到新加入且未确认的 Case，成功越过父 Chat 全 Case 门槛。外层 Case 查询和内层锁定 Plan 查询均使用当前读；数据确认 JOIN 同样使用当前读。批次号分配读取也锁定。
- Case 状态已是 PASS，但正常封存的子查询仍看不到人工 PASS，误拒正常结束。人工结论子查询显式锁读，外层锁读不足以更新子查询的快照。
- NEW_RUN 的同一 requestId 在等锁后漏读已提交关联，发生重复键错误而非幂等返回。关联记录查询使用当前读。

生成执行的历史执行、锁定 Plan 查询也使用当前读，避免等待后误判不存在和重复执行。编辑讨论轮次编号分配使用当前读，避免等待后的旧 MAX。

## 已有保护与观察接口边界

Plan 双确认的最新版本、已有确认记录已有 FOR UPDATE；结果建议保存和人工终判锁住 Workspace 通道后，collect(write=true) 对证据执行当前读，未发现同类绕过。正式 02/04/05 写入及 TA reset 的 epoch/cutoff 由另一个 agent 单独审查，此记录不替代其结果。

耐久 LangGraph 的 Chat/Case 状态已有当前读，关闭 Chat 的恢复写事件被阻断。workflowFacts 的普通读取在等锁后仍可能暂时返回旧阶段；它只更新观察状态和 checkpoint，不执行申请、发文或正式落库。下一次新的 read 事务重新采集并恢复阶段；同 eventId 幂等重放则按已保存历史响应返回，不保证最新阶段。草稿只读展示也可能暂时旧值。这些是显示/重试边界，未将它们误报为正式数据损坏，也未用全局隔离降级隐藏问题。写接口自己的 current-read 校验始终是业务授权依据。
