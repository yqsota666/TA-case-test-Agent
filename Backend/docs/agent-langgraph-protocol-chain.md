# Agent / LangGraph 操作链的中登协议规范

本规范记录2026-10-08用户明确的约束：**TA测试的业务操作链必须基于中登文件协议规范，每个申请动作能够落实到已核实的文件类型、业务代码和字段。自然语言业务描述不能直接作为可执行操作。** 本文供后续对照后端实现审查，不表示这些检查已全部实现，不改变现有接口或Plan结构。

文档基线为 `3470dca0`，整体流程见[Case全流程设计](../../docs/Case全流程设计.md)，运行及后续候选版本以本机 `PROJECT_VERSION_GUIDE.md` 和实时Git为准。本次仅增加规范，没有修改模型提示词、LangGraph节点、协议目录或业务执行代码。

## 1. 协议依据与能力边界

- 字段及文件布局先核对本地[中登V2.2原件（2026-03-20）](../../docs/protocol/中央数据交换平台开放式基金业务数据交换协议V2.2-20260320.doc)，再对照实际选择版本的协议目录、业务必填约束、编解码器与目标TA接入约定。其他协议版本使用各自原件与配置，不静默套用2.2。
- 公告、基金合同、用户需求用于确定业务规则、适用产品、变更前后行为及预期；它们不能单独证明中登协议有某个字段或业务代码。自建TA公告不自动适用于中登登记基金。
- 分开判断：协议是否可表达、目标TA是否受理、后端是否可生成/解析、是否可应用到正式账本、是否有实际结果证据。目录存在某业务不等于整个链路已实现。
- 协议原件与代码不一致时记录具体条款/字段及实现差异，不能因为代码已有某字段就反过来宣称协议支持。缺少映射的必需申请不得以猜测填补，也不得冒充可执行、已生成或已通过。

## 2. 操作链与文件批次的关系

一个场景对应其业务操作链；多个场景可以形成多条链，依赖共享时可组织成DAG。不固定比较数量、账户数量、业务动作或专属字段。

“差一天、恰好到期、多一天”是三条场景链；同一账户的两笔份额参与一次转托管，可以是一条链内的多笔明细。按确认后的实际场景、申请引用和依赖判定，不能仅按记录数或文件数计算链数。

同通道、同业务日期、同文件类型且依赖均已满足的申请合批，保留每账户、每申请与场景的独立关联和预期。合批不删除操作链，也不将多个账户缩成一条申请；不同业务日期或不同依赖不得假合并。

## 3. 每个动作必须可追溯

以下内容是审查时应能追溯的信息，可以来自现有Plan、协议目录、通道配置与证据关联，不要求本次新增一套JSON字段：

| 核对项 | 必须明确的内容 |
|---|---|
| 协议身份 | 协议版本、通道、登记机构及该业务适用范围 |
| 申请与确认 | 文件类型、发送/接收方向、申请业务码、对应确认业务码及是否确实存在确认 |
| 字段映射 | 原文条款或表格、标准字段名、业务语义、类型/字节宽度/精度、枚举、业务必填条件 |
| 输入来源 | 用户提供/已确认合成条件、正式资源、系统管理值、TA成功回传或额外输入；不能互相替代 |
| 关联与依赖 | 场景、账户、基金/类别、申请号、原确认号或逐笔引用；前置成功确认具体来自哪条申请 |
| 时间口径 | 申请日期、确认日期、份额起算日期、结果计算日期及业务日历约束 |
| 可观察结果 | 原始确认字段、正式数据、查询/日志/估值等具体证据来源与逐条预期 |

账户号、申请号等系统拥有的值由确定性服务生成或从正式绑定取值；需要TA确认产生的值不能由模型预先编造。字段名相似或包含“默认”不证明其作用范围为整个账户。

## 4. 新数据必须通过申请与成功确认建立

- 新模拟账户：`01开户申请 → 02成功确认并按现有机制应用`。同日同通道的新账户01与03同包生成，由OFI列出01先于03的处理顺序，未知TA账号不编造；系统用原申请日期与原申请单号精确引用同账户01。包内生成顺序不等于已获得成功回传，正式账户与持仓仍在02/04回传后同步。需要未来结果值或不同业务日期的操作必须分清实际提交包。
- 新模拟份额：`03认购/申购等合法申请 → 04成功确认并按支持范围应用`，形成可追溯的逐笔持仓。草稿份额、期望份额或直接写库不能冒充TA形成的正式持仓。
- 已有正式资源只有在来源、通道、状态与绑定可核验时才允许复用；不得以“已有草稿”省掉01/03。纯只读核对可以不构造新数据。
- 01/02与03/04之间的业务码对应、原申请引用、返回码及金额/份额核对必须由后端确定性处理。失败、歧义、乱序或未应用的回传不能满足后续成功依赖。
- 05按持仓核对目标决定是否需要；它不能代替开户成功、交易成功或费用计算。06分红、净值/估值等额外文件按所选版本及业务核实；未支持时如实说明。

## 5. “到指定持有时间”必须展开为日期安排

持有期按产品及目标TA规则，由该笔份额的起算日期和对应业务的计算日期得出。起点与终点分别核实，不能默认所有业务都用申购确认日/赎回确认日，也不能默认一年等于365天。

02是账户确认，不能把02与某份04之间的间隔当成持有期；文件下载、上传或接收的电脑时间也不能代替业务日期。04须区分申购确认与赎回确认等业务身份。

方案应明确各场景的起算日期、退出申请/确认日期及计日口径，并说明如何在测试TA形成这些日期：目标TA确实支持的历史回放、业务日推进，或可核实的正式历史持仓。净值、估值、费用计提与日历等必要输入随链路列明。不能把“等待到期”作为没有输入与执行依据的万能步骤，不能仅改回传日期制造历史持仓。

当前后端是否支持历史日期、日切与日历计算须单独查实现和实际运行证据；没有支持时不能宣称Agent可自动推进TA业务日。

## 6. 协议外条件与业务观察必须单独说明

销售侧计划、银行扣款、TA私有配置、估值导入、收益/费率公式及查询结果可以是测试所需的前提、额外输入或观察点，但必须标明来源与负责系统，不能伪装成中登申请动作。

如果必需准备动作无法通过中登文件表达，应先核实目标TA已确认的扩展或其他真实准备方式。没有依据时保留待核实条件，该场景不能归为完整可执行的纯中登文件链路；禁止虚构字段、滥用保留字段、用直接写库替代，或删除该动作假装方案已完整。

这不要求把所有业务预期转成后端字段。协议之外的收益、费用、记录有无等业务判断仍可由用户与AI讨论整理，再用实际业务输出核对；不能仅因没有协议字段就要求新增后端业务计算。

## 7. 反例与已核实映射

**账户级“红利再投资”设置：** 本地V2.2的01开户/账户修改字段表没有 `DefDividendMethod`；03的029业务在第7.22节、表25明确针对账户下的某只基金，`FundCode` 必填。因此不能把广发历史账户级设置直接写成中登01或03标准动作。历史账户级设置及迁移必须另有私有接口/配置依据。

**指定基金的分红方式：** `03/029 → 04/129`；`FundCode` 指定基金，`DefDividendMethod=0` 为红利转投、`1` 为现金分红，另有账户、申请编号、日期/时间、机构/网点和收费方式等必需字段。先开户/申购准备，再设置及接收确认；该映射成立不表示当前后端已实现029的正式应用。实际分红核对另需分红事件与06证据。

**两步转托管：** 在目标TA确实支持的范围内，`03/028转出 → 04/128成功 → 03/027转入 → 04/127确认`，转入关联对应转出凭据与逐笔信息。不能与一步026混淆，不能将某机构自建TA规则直接套到中登登记产品。带入/带出费用字段及落库来源必须另外核实，不借用名称相近的赎回费用字段。

## 8. 更新前后对比规则

同一逻辑测试数据、业务动作、日期口径和观察点，在明确标识的旧/新版本或旧/新配置下分别执行；独立环境的账号和申请号可不同，但必须有等价映射。不能在旧版做一种业务、新版做另一种业务而宣称只比较升级效果。

多个边界场景分别保留其操作链。若验证的是规则生效日切换，日期就是明确的目标变量；若验证的是实现升级，不能无说明再改变日期、费率或持仓。

“之前不记录，之后记录”可以是合法业务预期，但还须明确记录位置、字段/明细来源与对应金额；不能用开户或申购成功代替费用记录正确。公开资料只给现行规则时，标为规则回归，不编造旧TA曾有某缺陷。只有真实结果证据才能描述为已执行。

## 9. 后端合理性审查对照

| 审查位置 | 合理实现应满足 | 不合理实现的表现 |
|---|---|---|
| 讨论与Plan提案 | 根据需求、协议和实际能力拆链，未知的必需动作保留缺口 | 把“建立默认设置”“等到期”等话直接当可执行动作 |
| `define_plan_data` | 草稿只用于准备；新正式资源通过01/03建立 | 草稿或模拟余额直接当正式账户/持仓 |
| `define_plan_expectations` | 协议预期绑定真实字段，业务预期保留独立来源 | 给不存在的账户级字段赋值，或强塞所有费用判断到协议字段 |
| `validate_plan_applications`及协议编解码 | 校验版本、业务归属、业务必填字段、枚举/精度与系统值所有权 | 只检查JSON可解析或文件结构完整就宣称业务合法 |
| 文件时序与申请准备 | 逐条验证成功依赖及真实日期，按条件合批 | 看到02上传就放行所有03，或为了合批修改实际日期 |

| 结果核对 | 区分协议结果与业务观察，缺证据明确待核对 | 有04就认定费用正确，或把未执行的新旧对比写成通过 |

## 9. 草稿先行与可变销售商（2026-10-09）

- 普通讨论先给可修改的模拟条件，只询问会改变目标、核心操作链或真实结果判定方向的关键分歧；不要求用户逐项提供金额、日期、证件或费用样例。
- 模拟输入标明【模拟假设】，不冒充真实业务规则。方案里的逐文件模拟日期可以先供审阅；人类明确日期、改期、取消或待定要求优先。假设不能绕过TA能力、协议格式或未来回传值。
- 需求清楚时一轮完整讨论后即可整理草稿；没有讨论、历史不完整、协议契约无效时仍拒绝保存。两次明确确认和发文前校验保留。
- 每轮按当前会话认证读取工作空间通道候选。候选不是已选销售商；用户或已保存方案的明确选择优先。不写死销售商代码，不擅认直销/代销，不跨工作空间或不同通道沿用账号、文件命名与私有交付规则。未选择销售商不阻止其他草稿条件准备，发文前必须选择实际合法通道。
- 用户修改条件时相关数据与预期一起更新；旧版本和已确认历史不自动改写。
